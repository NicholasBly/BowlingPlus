# 120 FPS mode

Status: shipped in BowlingPlus since 1.2.0. Off by default; a switch in **Display & startup**.
Difficulty to port: **1 (easiest)**. It is a settings value plus one build flag on iOS.

## What it does

The game draws menus at 30 FPS and gameplay at 60 FPS on phones. With the switch on, both run at 120 FPS on a 120 Hz screen. Uses more battery.

## How the game picks its frame rate (1.907 build)

- `Client.Core.Constants` has static ints for the frame rates:
  - `FB_FRAME_RATE` = 200 (PC / old Facebook GameRoom build; not used on phones)
  - `MENU_FRAME_RATE` = 30
  - `GAME_FRAME_RATE` = 60
  - the fourth value, `MAX_FRAME_SCORE` = 30, is unrelated to speed
  - the values are a 16-byte constant at VA `0x3e9f8d0`, copied in by the class's static constructor.
- `GetFPSForGameMode()` returns `GAME_FRAME_RATE` on iPhone (platform 8) and Android (platform 11), and the PC value otherwise. `GetFPSForMenuMode()` does the same for menus.
- These values are passed to `Application.targetFrameRate` by `Loading.Start`, `RunPsycsTest.StartFun`, `RunPsycsTest.restartGameComplite`, `FloatingMenu` and `HTHLobbyManager`. They also set `QualitySettings.vSyncCount = 0`, which iOS ignores.

## What BowlingPlus does

Shared native code (`src/Game.mm` and `android/native/Game.cpp`, same block on both):

- `FpsTick()` runs every 30 frames. With the switch on, it saves the two table values, writes 120 into `MENU_FRAME_RATE` and `GAME_FRAME_RATE`, and sets `Application.targetFrameRate` to 120 if it isn't already.
- With the switch off, it writes the saved values back and sets the target to the game's game rate.
- While BowlingPlus's own menu is open, the lane behind it is capped to 30 FPS (1.6.1). Drawing the lane at 120 FPS behind the menu took the GPU the menu's scrolling needed.

Platform parts:

- **iOS:** the game's `Info.plist` key `CADisableMinimumFrameDurationOnPhone` is `false` in the stock IPA, so iOS holds the app at 60 Hz whatever the game asks for. BowlingPlus's build tool (`tools/inject_ipa.py`) sets it to `true`. Without it, the game reports a target of 120 and runs at 60 (seen on a phone, 1.6.1).
- **Android:** `android/java/com/bowlingplus/BP.java`, `applyFps()`, sets the window's `preferredDisplayModeId` to the display's fastest mode with the same resolution (Android 6.0 and up). Without it, the app doesn't ask Android for the 120 Hz mode.

## Why it's safe to run at 120

The game's physics runs on a fixed timestep (7.5 ms in this build; see `pin-physics/PHYSICS_SETTINGS.md`), separate from the drawing rate. So the drawing rate doesn't change how shots play out. This follows from how Unity's fixed step works. It has not been measured separately on a phone.

## Testing status

- **iOS:** the plist key was confirmed on a phone (1.6.1). Smoothness has only been reported by users; no frame-time measurement is recorded.
- **Android:** the display-mode request and the table change compile and pass the CI build. No phone test is recorded.

## Porting to the official game

1. Add a settings value for the frame rate target (e.g. 60 / 120) and read it where the game chooses its rates.
2. Set `MENU_FRAME_RATE` and `GAME_FRAME_RATE` from that setting, not in a shared constant.
3. iOS: ship `CADisableMinimumFrameDurationOnPhone = YES` in the app's `Info.plist`. This is the step most likely to be missed.
4. Android: request the display's fastest mode on the game's activity window when the setting is on.
5. Cap the frame rate of the lane behind any in-game overlay that scrolls, so the overlay stays smooth.
6. It's a display setting. Our reading is that it doesn't change the physics, so it can work in every mode; confirm that on your side before shipping.

## Duplicate-fix note

If the official game adds its own 120 FPS option, hide BowlingPlus's switch on builds where that option exists. `FpsTick()` already stores whatever it reads as the original values, so it's harmless if both run; it just shouldn't be shown twice.
